# box_cache 仕様書

状態: 初期仕様（実装前）  
更新日: 2026-10-28

## 1. 目的と対象

プロジェクト名とキーを指定して、ファイルとしてデータを保存・取得する簡単なキャッシュシステムを提供する。
Pythonパッケージとして `pip install` して使用することを想定する。

初期の対応OSはWindowsのみとする。macOSなどの対応・検証は対象外とする。
READMEは利用者向けの説明に用い、設計上の仕様・制約・検討事項は本書に記載する。
ソースコードと実行時のディレクトリ構成は [architecture.md](architecture.md) に記載する。

## 2. キャッシュの基本構造

- キャッシュは「プロジェクト名」と「キー」の組で識別する。
- プロジェクト名も識別の一部であり、キーが同じでもプロジェクトが異なれば別のキャッシュとして扱う。プロジェクト名には、人がファイルを検分しやすくする役割もある。
- プロジェクト名の大文字小文字を自動で統一しない。同じキーに対して、既存のプロジェクト名と大文字小文字だけが異なる名前で保存しようとした場合は、警告を出して停止する。版の日時が異なってもこの検査を行う。
- キーは任意のPython文字列（`str`）とする。空文字、日本語、制御文字なども許容し、内容の正規化や大文字小文字の変換を行わない。ハッシュ化に使う文字列のバイト表現は、すべての `str` に対応する方法を実装時に固定する。
- 保存する本体の対応型は `bytes` と `str` とし、読み出しでは保存時の型で返す。JSONは文字列として扱い、パースは呼び出し側で行う。
- 同じ組に対する再保存では新しい版を追加する。過去の版は重要なエビデンスとして保持し、上書き・自動削除しない。
- 通常の読み出しでは、その組に対応する保存日時が最も新しい版を返す。
- 保存時に呼び出し側が渡すのはプロジェクト名、キー、ファイル本体のみとする。元データの取得は呼び出し側の責任であり、本システムでは扱わない。
- 日時は本システムが記録する保存日時とする。キーのハッシュには含めず、メタデータに保持する。ファイル名にも保存日時を含める案とする。
- 各キャッシュは、メタデータファイルと本体ファイルから成る。
- キャッシュがない場合の読み出し結果は `None` とする。
- メタデータには最低限、プロジェクト名、キー、保存日時を含める。
- キャッシュディレクトリ内にはサブディレクトリを作らず、すべてのファイルを直接配置する。
- プロジェクトごとのサブディレクトリも作らない。

メタデータの形式案:

```json
{
  "project": "weather",
  "key": "tokyo",
  "saved_at": "2026-10-28T03:00:00.000Z",
  "size_bytes": 5,
  "sha256": "2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824"
}
```

## 3. 設定と保存先

### 3.1 設定ファイルの配置

設定ファイルは、Windowsのユーザー別の固定位置に置く。

```text
%LOCALAPPDATA%\box_cache\config.json
```

`LOCALAPPDATA` は実行環境の値から取得する。ユーザー名を含むパスをコードに固定しない。
パッケージのインストール先、仮想環境、呼び出し元プロジェクト、カレントディレクトリには設定を置かない。
AppData内で作成・更新する対象は、本パッケージ用と確認できた領域に限定する。

設定ファイルの形式案:

```json
{
  "application": "box_cache",
  "config_version": 1,
  "cache_dir": "D:\\my-cache"
}
```

`application` と `config_version` は、設定の用途と対応可能な形式を確認するために使う。
これらは偶発的な取り違えを防ぐための識別情報であり、改ざんを防ぐ仕組みではない。

### 3.2 キャッシュ保存先

- キャッシュ本体の保存先は設定ファイルの `cache_dir` で指定する。
- 設定ファイルには絶対パスを記録する。
- 設定時に相対パスを受け付ける場合は、その時点で絶対パスに変換して保存する。
- プロジェクト内の設定などによる保存先の自動上書きは行わない。
- 未設定、設定破損、保存先の利用不可の場合は、別の場所に自動保存せずエラーにする。
- 読み取り時や書き込み時に、未設定の状態から暗黙に初期設定を行わない。
- 保存先の変更では設定のみを更新し、変更前のキャッシュを移動・削除しない。
- 不正なパスや利用できないパスは、対象パスと理由を示す警告を出して処理を停止する。設定変更時の検証に失敗した場合は、既存設定を維持する。

同じOSユーザー・同じマシン・同じ `LOCALAPPDATA` の環境では、設定が変更されない限り、どの作業ディレクトリや仮想環境から呼び出しても同じキャッシュ保存先を使う。
別ユーザー、別マシン、コンテナ、および環境変数を変更した実行環境まで同じ保存先となることは保証しない。

## 4. 既存ディレクトリの保護

### 4.1 設定ディレクトリ

初期設定時に `%LOCALAPPDATA%\box_cache` の存在と用途を確認する。

| 状態 | 動作 |
| --- | --- |
| 存在しない | 専用ディレクトリと設定ファイルを作成する |
| 本パッケージの対応形式の設定が存在する | 既存設定として扱い、明示的な設定操作で更新できる |
| 存在するが識別情報がない、読めない、または一致しない | 変更せず、対象パスと理由を示してエラーにする |
| 同名の通常ファイルなどが存在する | 変更せずエラーにする |

既存の空ディレクトリも、用途を確認できなければ自動で流用しない。
初期設定の失敗によって識別情報のないディレクトリが残った場合も、同じルールで扱う。

### 4.2 キャッシュディレクトリ

キャッシュ保存先にも専用の識別ファイルを直接配置し、本パッケージ用の領域であることを確認する。
識別ファイルの名前と形式は実装前に決定する。

- 保存先が存在しなければ、新規作成して識別情報を記録する。
- 既存の保存先は、識別情報が一致し、対応形式である場合に使用する。
- 識別情報がない、不一致、破損、または未対応形式の場合は変更せずエラーにする。
- 他用途のファイルを削除したり、既存ディレクトリを自動で取り込んだりしない。
- 設定領域とキャッシュ領域は別のディレクトリとする。

存在確認後に別プロセスが作成する可能性も考慮し、作成時の衝突では既存内容を上書きしない。
ディレクトリの衝突時は、対象パスと理由を示す警告を出して処理を停止する。

## 5. 運用方針

### 5.1 破損したキャッシュ

- 破損が検出されたキャッシュは、有効なデータを返さず、キャッシュなしとして扱う。
- 最新版が破損している場合はワーニングを出し、ログにも記録する。キャッシュなしとして `None` を返す。過去の版への自動フォールバックは現時点では採用しない。
- 破損したことをメタデータに記録する。
- 破損した版もエビデンスとして保持し、再保存では別の版を追加する。
- データベース相当の復旧精度は目指さず、破損したデータを有効なキャッシュとして使わないことを優先する。
- 保存時に本体のバイト数とSHA-256をメタデータに記録し、読み出し時に実データと照合して破損を検出する。キーのハッシュと本体のハッシュは用途が異なる。
- メタデータ自体が欠落・破損している場合もワーニングを出してログに記録し、`None` を返す。破損したファイルは保持し、メタデータへの破損記録を無理に行わない。
- メタデータに記録する破損情報の項目・形式は未決定とする。
- 設定エラーやアクセス権の問題は、キャッシュの未登録・破損とは区別し、警告を出して処理を停止する。

ログは設定領域ではなく、設定されたキャッシュディレクトリの直下に置く。
ログのファイル名・形式と、ログを書き込めない場合の扱いは実装前に確定する。

### 5.2 初期版の範囲

有効期限、容量制限、自動削除は初期版に含めない。
明示的な削除操作は必要性を再検討する。現時点では初期版の必須APIに含めない。
過去の版はファイルとして保持するが、過去の版の一覧・指定読み出しAPIは初期版に含めない。

## 6. 提案中の詳細

以下は会話中に挙がった設計案であり、実装前に確定する。

### 6.1 ファイル名とデータ形式

- キーだけをSHA-256でハッシュ化し、プロジェクト名はファイル名にそのまま含める。
- メタデータは `<プロジェクト名>_<キーのハッシュ>_<日時>.json`、本体は同じ幹の `.data` とする。
- プロジェクト名はWindowsのファイル名の一部として問題なく使用できるものに限定する。不正な名前を自動で別名に変換しない。長さ、区切り文字を含む場合の解析方法、Windows上で大文字小文字だけが異なる名前の検出方法などの詳細は実装前に確定する。
- ファイル名の日時には保存日時を使用する。ミリ秒精度を候補とし、書式は実装前に確定する。同一プロジェクト・キー・日時のファイル名衝突は異常な運用として扱い、警告を出して保存処理を停止する。連番付与や自動再試行による衝突回避は行わず、既存の版を上書きしない。
- 本体は任意のバイト列を扱う。
- 呼び出し側による事前のファイル作成やパス指定を必須にしない。
- 文字列の保存表現はUTF-8を基本とし、メタデータに保存時の型を記録する。サロゲートを含む文字列の扱いなど、変換の詳細は実装時に固定する。
- 文字列がJSONかどうかの自動判定・自動パースは行わない。
- 初期の本体入力は `bytes` と `str` とする。型情報の形式は実装時に決定する。
- 保存日時はUTCのISO 8601形式でメタデータに記録する。
- 保存日時は本システムが自動で付与し、呼び出し側からの日時指定は要求しない。キャッシュの読み取りでは更新しない。

配置例:

```text
D:\my-cache\
  <識別ファイル>
  weather_<キーのハッシュ>_20261028T030000Z.json
  weather_<キーのハッシュ>_20261028T030000Z.data
  weather_<キーのハッシュ>_20261028T040000Z.json
  weather_<キーのハッシュ>_20261028T040000Z.data
```

### 6.2 APIと設定コマンド

基本操作の候補:

```python
put(project, key, data)
get(project, key)
```

利用者がAppDataを手作業で編集せず設定できるコマンドの候補:

```powershell
box-cache configure --cache-dir D:\my-cache
box-cache config show
```

ファイル本体の受け渡し方法、APIの戻り値・例外、コマンド名の最終決定は未了とする。

### 6.3 書き込みの整合性

以下を実装案とする。

1. キャッシュ直下に、本体とメタデータを一時ファイルとして作成する。一時ファイルは読み出し対象にしない。
2. 両方の書き込みを完了してファイルを閉じる。
3. 本体を最終ファイル名で公開する。
4. 最後にメタデータを最終ファイル名で公開し、この操作を版の保存完了の目印とする。

読み出しは公開済みメタデータを入口として版を選び、本体のサイズとSHA-256を検証してから返す。メタデータを最終名へ公開する操作は、途中の内容が見えない方法を用いる。
書き込み中は、それ以前に保存完了している版を読み出せる。
公開済みメタデータがあるのに本体がない場合は、破損として扱う。
メタデータの公開前に中断した場合の一時ファイル・本体は保存未完了として保持し、読み出し対象から外す。実行中の保存と中断した保存の区別、および通知方法は実装時に決定する。

既存ファイルの有無を事前確認するだけでは競合を防げないため、作成・公開の操作自体が既存ファイルを上書きしない方法を使う。衝突を検出したら警告を出して停止する。
同じキーへの並行保存と、プロジェクト名の大文字小文字の競合確認には排他制御を検討し、確認と保存の間に競合する変更が入らないようにする。
本方式は書き込み途中の読み出しを防ぐための案であり、電源断などに対するデータベース相当の復旧保証は行わない。
最新版は保存日時で選択する。システム時計の巻き戻りによって後から保存した版の日時が古くなった場合も、保存日時が最も新しい版が読み出される。
最新版が破損している場合は5.1節の方針に従い、ワーニングとログ記録を行って `None` を返す。
